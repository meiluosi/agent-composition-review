# 模型差异与指导增量：复盘

**本轮决定：不升级 v4，不继续追加这版指导的调用，先修正评测的区分度与正常标签。** 这次没有获得 Skill 超过普通工程清单的证据；也不能证明范畴论路线无效，或证明弱模型更受益。默认 Skill 与 v4 候选保持原样，后续不通过增加入口文字或拆更多 Skill 来追求正分数。

原执行器在 64 次后发生分类器误熔断：把日志文件名中的 `401` 误判成鉴权状态。原失败记录保持不变；[独立恢复登记](../evals/iterations/model-interaction-2026-10-04/RECOVERY_PLAN.md)只允许继续未开始的 80 项，总上限仍是 144。结果需要分阶段解释，不能描述成无中断的执行。

恢复新增 36 次后按停止规则结束。最后一次在 360 秒上限被执行器终止，伴随模型目录刷新超时及遥测发送失败；这些是真实辅助服务请求错误，但无法确认推理通道故障或超时因果。保留机器 transport 分类，不再恢复。累计 100 次尝试、97 次有效完成、96 次成功交付，44 项从未开始；不是 144 次完整实验。100 份产物重验与原行为签名一致，原始日志哈希在本机全部核验。

**“弱模型可能获益”仍是待验证假设。** Luna 的配对 C−A 为 +8.3 个百分点，来源是 m10 首次基线修复遗漏旧版本处理；普通清单同样解决，因此没有范畴论指导的额外收益证据。该题第二次重复尚未运行，不能声称已验证稳定性。只有一个家族呈正差，也未满足预先要求的跨家族条件。

**Astra 的分数下降不能直接证明 Skill 损害推理。** 其 A 有一次未完成，C 有两次未完成，留存源码都通过了原验收；其中一次 C 的未完成伴随辅助网络异常。完整配对的 C−A 为 −4.2 个百分点，交互差值因此为 +12.5 个百分点，但它混合了有限任务差异和交付失败，不足以建立模型强弱的因果解释。没有把失败改成成功，也不将基础设施伴随现象当作能力失败。

**有可观察成本，没有对应的额外成功。** Luna B/C 覆盖相同 17 项、用量均完整，C 输入 token 为 2,555,103，B 为 2,046,542，增加约 24.85%；两组均 17/17 成功。输入包含缓存，不能折算实际收费，也不是普遍的效率结论。Astra C 两次用量缺失，不能把缺失算零，或据此比较完整成本。

观察到的基线通过率较高，但本轮没有完成 24 次/单元，因此不能宣布达到预注册的 22/24 饱和门槛。更准确的判断是：现有验收显示的改进空间有限，同时存在覆盖遗漏，当前数据不足以区分强模型天花板、指导增量和测量问题。全部门槛保持冻结，不进入独立保留集确认。

## 先分开三个问题

“强模型已会做，所以 Skill 没增益”“指导本身产生额外负担”“验收或正常标签不正确”可以同时存在。跨模型对照只能在相同任务、工具、时间预算和指标下观察指导增量，不能自动决定哪一种解释适用于所有 Agent 系统。

本轮把业务要求和可选工具固定，比较无额外指导、普通工程清单、当前 v4。它测整个指导包，不单独识别某条范畴论原则、目录拆分或工具本身的价值。Luna 被选为较低成本模型；它是否在这组任务上更弱，需要看实际基线，不能从产品定位推定。四个自建标准库家族也不能代表此前 Who&When 外部轨迹归因任务。

## 两个正常标签问题改变了什么

**m08：解析成功不等于合法 JSON。** 冻结参考使用 Python 默认 `json.loads`。它接受非标准常量，又把重复字段折叠成最后一个值，因此 `{"event":NaN,"event":"done"}` 能绕过后续形状校验。Astra 无额外指导的一次执行发现了真实缺陷，原指标却会因“normal”标签把其 violation 算作误报。另一些回答仅要求拒绝重复字段；那是题面没有明确的策略，不能混为同一个发现。[事后反例与修订参考](../evals/model_interaction_followup/README.md)

**m02：同是字符串，也可能不保留原值。** 题面只要求非空 Python 字符串 ID/worker，SQLite 却无法直接编码部分代理码点；默认 JSON 往返还会合并代理码点对，使 payload 字符串变化、两个不同键变成一个。Astra A/B 的已完成修复解决了观察到的边界。Astra C 留存代码也解决了它们，但该次超时，仍不算成功交付。Luna 的布尔值拒绝和超大时间存储改动针对题面之外的输入，不构成同样的真实发现。[范围与七来源复核](../evals/model_interaction_followup/lease_review.md)

这些是看过结果之后的开发探针，不能伪装成预注册或保留集成绩。我们保存原题、原分数和失败状态，再单独披露标签问题；不删除“难看”的运行，不用事后分数重写主要比较。原验收全通过只表示满足那组检查，无法替代题面的全部承诺。

## 执行器也出现了语义角色混淆

原错误分类器在完整 stderr 字符串中查找 `401`。一次本来耗尽执行时限的调用，其日志路径恰好包含这串数字，于是被标为鉴权失败并触发停止。独立回读没有找到真正的 HTTP 401 或鉴权终止事件。它说明数字外形相同，不代表证据的角色相同：路径标识、时间戳和 HTTP 状态必须分开。

恢复分类器要求错误码有 HTTP/status 语境或真实错误措辞，并对原反例及真实服务错误分别回归。原调用没有写出指定最终文件，仍然失败；原因纠正不会把它改成成功，也不会补跑这一条。该修订是评测软件的修复，不能作为 Skill 帮助模型的效果证据。

## 范畴论框架应如何继续使用

这次字符串反例适合说明框架的用途，也说明它的限度。若业务要求精确保留原值，编码和解码需要满足 `decode(encode(x)) = x`。这一等式来自业务要求，并不是“用了范畴论”就自动成立。

观察到两个不同 Python 字符串被编码为同一表示后，任何只看到该表示的解码器都不可能恢复两个不同原值。可行选择是明确缩小允许的字符串域，或者采用保留这些区别的表示；不能在已经丢失信息的结果上补一个类型名就获得保真性。类似地，返回一个符合字段形状的字典，也不能证明原始字节属于约定的 JSON 语言。

因此，理论在这里应帮助提出可执行的问题：允许的输入集合到底是什么；转换是否可能失败；哪些区别必须保持；应该比较哪些业务观察。将这些问题落实为反例、往返测试和明确的异常策略，才能检验模型是否真的解决了问题。抽象词汇和结构报告本身不应计分。

这不要求立即扩大入口正文或拆成更多 Skill。保持一个主入口与按需参考，后续修改应对应具体失败条件和独立验收。当前共同工具组也拿到了结构脚本，因此即使转向边界检查工具和案例库，也只能称为待验证的产品方向，不能宣称本轮已经证明工具收益。

## 后续实验需要先解决的条件

先校准任务与评分，再选择是否验证指导：把 Python 字符串、Unicode 标量、合法 JSON 字节等不同集合写清楚；把成功、失败和未定义行为区分开；在宣布正常参考前加入会破坏关键保持关系的反例。有限测试仍不是完整正确性证明，应持续保留新发现。

若再做模型差异实验，应在另行冻结的新任务上获得足够区分度，并保留普通清单条件。重复运行已见病例、增加术语或单纯更换更小模型，都不能替代这一条件。本轮之后不会自动追加确认性调用；已见案例也不会改名为独立保留集。
