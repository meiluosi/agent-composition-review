# 自主建模复盘：完成条件与评测覆盖需要更精确

本轮保存了三类运行机制的代码修改与自主建模产物、原失败记录、独立评审恢复批次和额外反例。**仍没有足够依据升级 v4。** 原验收在有效完成任务上三组均为 10/10，结构评审对这些模型也均满足三个有限判据；事后探针中 B 与 C 相同。数字见 [完整报告](../evals/iterations/code-repair-2026-09-30/REPORT.md)。

## 两处正常标签错误

我们把通过有限验收的参考实现当成了完整正常实现，这是本轮评测设计的错误。

- c04 的主体插入正确，但最外层 RELEASE 失败不在原处理范围中，可能留下失败批次。三组都主动发现了提交阶段的遗漏。
- c06 会在清理期间再次取消子任务。原测试分别检查了失败和取消，却没有组合检查有关交错。

两种错误均用真实运行复现，并提供了修订正常参考。原输入和分数没有改写；正常保持只能在 c02 图任务上作有限解释，每组两次都保留原代码。修订的事务和异步正常参考尚未作为新输入进行模型对照，不能宣传三类正常系统都已验证无误报。

## 格式、覆盖判据与满足契约

原 36 次代码尝试有 30 次有效完成，6 次因额度限制中断；三组各 10/12，完成的 10 次均通过原行为验收。原 36 次盲评也因额度限制失败，没有语义判断，不能把其 0/12 当成语义错误率。

额度恢复后另行登记 31 次评审，使用原提示和判据，保留不同 CLI 版本与时间。全部有效，93 项判断均为 covered。这里包括一份中断任务的模型，不能据此升级原任务状态；另五份缺失模型没有生成假评审。恢复工作没有补跑代码修复。

维护者回读发现，covered 不能说明完整契约已满足。例如 c06/A/1 用“未完成 Task 数为零”表达清理完成义务；补充执行中 Task 已终止，业务清理却被再次取消打断。部分事务模型已声明清理失败时不保证恢复，这类范围内描述可以成立，但实现仍未覆盖全部原始文字要求。原评审保留，分歧及更强解释的限制见 [复核说明](../evals/iterations/code-repair-2026-09-30/CURATOR_REVIEW.md)。

后续需要显式区分目标契约、实现推断、已经执行的验证，以及未知或不满足的义务；不能仅依赖“保证”一类字段名。

## 框架如何继续落实

本轮支持优先精化三个部分，详见 [完成边界分析](completion-boundaries.md)：

1. **资源归属与完成条件**：内部返回、提交完成、任务终止、清理完成分别建模；所有权决定哪些结束动作合法。
2. **观察粒度**：done 或 success 可能合并了业务上不同的状态，验证不变量需要保留区分它们的证据。
3. **假设与保证**：明确环境能否回滚、是否存在调用者外层事务、允许何种取消交错；无法满足的情况保持未知或明确失败。

现有 v4 已包含所有权、取消、状态与效应的方向。本轮主要暴露了具体声明和验收的精度不足，尚不能证明加长入口、增加理论目录或拆成多个 Skill 会提高效果。

继续保留一个主 Skill 与按需参考模块；v4 仍为候选，主包不升级。新增探针是评测资产，不是已安装的新运行能力。后续修改指导需用修订正常参考和未参与设计的任务先冻结判据，再检验收益；本轮交错不能冒充新的保留集。
