# LangGraph 组合故障诊断

目标不是“讲一遍架构”，而是回答三个问题：**哪条边界先坏了、证据是什么、最小的修法是什么**。`acr` 帮你把边界缩小到具体文件行号或轨迹事件；判断和修复仍然要回到代码与实际运行。

## 何时使用

出现下面任一情况时加载本技能：

- 子图、节点单独运行正常，接进父图后报 `InvalidUpdateError`、状态被覆盖或字段丢失。
- 并行分支（fan-out）写同一个状态键，结果取决于谁后完成。
- 重试、回滚、checkpoint 恢复后，同一个工具被重复调用，产生重复副作用。
- 缓存命中后不再重新采样，投票/多次生成实际只发生了一次。
- 多智能体或多节点合并结果时，某个字段没被合并进去，下游读到空值。

不适用：普通文案润色、孤立算法题、只需要查 LangGraph API 用法的场景。也不要把节点内部的单点 bug 硬说成“组合问题”。

## 第一步：把症状收敛成一个边界

先要一次**可复现的失败**：输入、版本、报错/错误输出、相关代码路径。没有失败样本时先构造最小复现，不要直接通读整个仓库。

| 你看到的 | 优先怀疑 |
| --- | --- |
| `InvalidUpdateError: At key 'x'` | 同一 superstep 有多个写者；子图回传完整状态；缺 reducer |
| 子图跑完父图字段变旧/消失 | 子图没有 `output_schema`，把完整快照当补丁回传 |
| 并行分支结果不稳定 | 共享单值键被并发写，或 reducer 不可交换 |
| 同一笔操作执行两次 | retry/恢复包住了非幂等副作用；缺幂等键 |
| 缓存后结果“太稳定” | cache key 没包含采样参数/序号，复用与重采样混在一起 |
| 收尾后仍残留半成品 | 完成边界没定义，失败路径没有清理/回滚 |

## 第二步：用 acr scan / trace 取证

```sh
acr scan path/to/graph.py            # 静态检查构图代码
acr trace path/to/trace.jsonl        # 检查一次失败轨迹
acr trace trace.jsonl --resume-at 4  # LangGraph debug 流没有 resume 事件时，指向恢复前最后一条事件
acr scan . --json > scan.json        # 机器可读，便于逐条核对
acr trace trace.jsonl --json         # 输出时间线与证据事件 ID
```

`acr rules` 会显示每条规则是 `grounded` 还是 `experimental`；experimental 的 finding 只能当线索，不要当已验证结论。

读 finding 时按这个顺序核对，不要看到规则 ID 就改代码：

1. **证据**：打开 `file:line` 或事件 ID，确认它真的是这次故障涉及的代码/步骤。
2. **复现**：用最小输入跑一次，确认报错或异常状态可重复出现。
3. **归因**：区分三种情况——`已证实`（能解释因果链）、`设计如此`（边界是有意的）、`证据不足`（需要更多运行/日志）。
4. 只有“已证实”的 finding 才进入修复；其余写进报告的待验证项。

如果环境里没有安装 `acr`，明确说明“未运行扫描”，改用 [references/rules.md](references/rules.md) 的规则手工检查；不要把预期输出当成已运行结果。

## 第三步：做最小修复

按 finding 指向的边界选一种模式；一次只改一个边界，改完立刻验证。完整代码见 [references/fix-patterns.md](references/fix-patterns.md)。

| 边界 | 最小修复 | 不要做 |
| --- | --- | --- |
| 子图输出越界 | 子图声明 `output_schema`，只列自己写的键 | 为消错把子图改成串行、丢掉并行 |
| 并行写同键 | 给该键加可交换 reducer，或收敛为单写者 | 给单值键硬塞“最后写者赢” |
| 外部副作用重复 | 业务幂等键 + 重试只包幂等操作 | 直接关掉 retry，掩盖不稳定 |
| 缓存语义错位 | cache key 纳入采样参数/序号，区分复用与重采样 | 一律禁用缓存 |
| 完成边界模糊 | 定义“什么算完成”，失败回滚/标记，清理可重入 | 只加日志，不处理半成品 |

修复时保留原有的上下文读取和并行关系：`output_schema` 只收窄输出，不削减输入。改完在代码旁注明对应的规则 ID，方便后续回归。

## 第四步：加回归测试

至少覆盖四条：

- 复现旧故障的输入仍会走到原来的边界（修复后不再报错/不再重复副作用）；
- 正常路径结果不变（字段值、并行关系、上下文读取）；
- 同一节点/工具重复执行时不产生第二次外部效果；
- 失败后重试或恢复，只执行一次外部写，且清理后能再次运行。

不要用“测试全绿”代替“旧故障被复现过”。没有复现过的修复无法证明修对了。

## 第五步：输出一页报告

诊断任务默认交付这一页；用户只问原因时就停在报告，不要擅自扩大重构范围。

```markdown
## 结论
一句话：哪个边界坏了，影响是什么。

## 症状与复现
输入 / 版本 / 报错原文 / 最小复现路径。

## 证据
acr finding（规则 ID、文件行号或事件 ID）+ 运行观察。
区分：已证实 / 设计如此 / 证据不足。

## 根因
触发条件 → 边界证据 → 被破坏的契约 → 业务后果。

## 最小修复
改了什么（output_schema / reducer / 幂等键 / 缓存键 / 完成边界），
以及为什么没有扩大到其他模块。

## 验证
跑过的命令与结果；回归测试覆盖了哪些旧行为。

## 剩余风险
没验证的输入、未解决的 finding、需要线上数据才能确认的部分。
```

## 证据纪律

- **证据不足就说不知道。** 只有一次运行、没有日志、无法复现时，给出“还需要什么证据”，不要用框架术语补全因果。
- 静态扫描只看代码结构，看不到实际合并结果；轨迹只看发生过的一次运行，不能证明其他输入下同样成立。
- 规则命中 ≠ 根因。根因必须能解释“为什么单独跑正常、组合后坏”。
- 不要编造命令输出、文件行号或事件 ID；引用 finding 时回到原始输出核对。
- v0.1 的边界：Python AST 分析，面向 LangGraph 1.x；不是运行时追踪器，不会自动改代码，也不宣称 benchmark 提升。评测历史是另一份档案，不属于产品承诺。
