# ACR002 · 并行分支写同一状态键且无 reducer

**级别**：high（静态检查，构图层）
**命令**：`acr scan <path>`

## 症状

- 图从 `START` 扇出多个分支，运行时在某个键上报 `InvalidUpdateError`。
- 两个并行节点都返回同一个键；谁生效取决于完成顺序，重跑结果不稳定。
- 单看每个节点都“只写自己的字段”，合起来却冲突。

## 为什么发生

LangGraph 的每个 superstep 中，同一个状态键只能收到一个更新。若并行分支都写同一个键，而该键的 schema 没有 `Annotated[..., reducer]`，框架无法合并，只能报错；如果框架/代码在某处悄悄做成“最后写者胜”，则会丢数据。

这不是“并行本身有错”，而是**共享可变单值**在并行下没有定义合并语义。

示例来自仓库测试 fixture（`acr` 0.1.0 真实输出）。对 [examples/langgraph-subgraph-leak/broken.py](../../examples/langgraph-subgraph-leak/broken.py) 运行会同时报告 ACR001 与 ACR002；修复子图输出边界后两条一起消失。

## 最小修复

```python
import operator
from typing import Annotated, TypedDict

def merge_unique(left: list[str], right: list[str]) -> list[str]:
    # reducer 需可交换、可重复执行：并行顺序不应改变结果
    return sorted(set(left) | set(right))

class State(TypedDict):
    findings: Annotated[list[str], merge_unique]
    total_cost: Annotated[float, operator.add]
```

若该键在业务上只能有一个值，就不要加“最后写者赢”，而应把写者收敛到一个节点，或把并行结果先收集到列表再统一决策。

## 验证

- 同一输入重跑不再报 `InvalidUpdateError`。
- 交换分支完成顺序，结果不变。
- reducer 重复执行（恢复/重试）不会产生重复数据。

## 误报边界

- 同一 superstep 里只有一个分支会实际执行（另一个在条件边上被跳过）：运行期不会冲突，可只记录提示。
- 该键语义就是“最后写者胜”且业务接受丢数据：这不是框架问题，但仍建议显式串行化，避免依赖完成顺序。
- 键已经有 reducer，只是 scan 没识别出 `Annotated` 的写法：以运行结果为准，可报告为工具误报。
