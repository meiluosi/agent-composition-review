# 评测协议

## 两种问题必须分别回答

**工程回归**：复现是否还有效，修复是否保留结果与副作用语义，技能格式和引用是否正常？`scripts/run_evals.py` 和 CI 负责这一层。

**模型行为**：加载 Skill 是否让模型更准确地诊断、选择更有用的问题、提交更充分的修复？需要真实模型运行与对照；当前仓库不把这一层伪装成无密钥自动测试。

不要把通过的测试方法数量、理论名词数量、报告长度、总 token 数或描述的“完整度”当作诊断能力。

## 案例登记与分组

每个案例记录稳定 ID、失效家族、来源 URL/版本、本地实际版本、复现代码、目标不变量和证据等级。区分公开 issue、官方行为示例、人工构造和真实业务事件。公开 issue 是问题报告，仍需本地验证；不要自动当作已被上游确认的缺陷。

失效代码、正常相邻案例和不充分修复应同时考虑。例如：完整响应缓存可能替代新采样，但输入前缀缓存不能仅凭答案相同判为故障；修复读未命中也不能把所有已有记录变成未命中。

数据按**失效家族**划分，不能把改字段名或参数的同源案例伪装成保留测试。用来写规则、看过答案或反复调优的案例都归开发集。所有当前公开案例均为开发集，尚无保留集。

未来可将新案例的答案保存在 `evals/runs/private/` 或仓库外，并限制执行者可读路径。公开问题可能已经进入模型知识，隐藏答案文件不等于保证模型从未见过该问题。应明确这种污染风险。

## 一次模型评测怎么做

1. 先冻结输入、业务约束、验收器、失败判据及相关文件哈希，再运行执行者。
2. 至少设置当前 Skill 与不加载 Skill 的对照；修改规则时增加上一版本。使用独立上下文，同一模型版本、推理设置、工具权限、预算和输入材料，交错组别顺序。
3. 只让执行者看到用户原始请求和允许材料。不要提前给根因、修复、黄金答案或对方输出；允许读取哪些库文档也须两组一致。
4. 把轨迹、澄清问题、最终回答、代码补丁、实际命令和测试结果保存下来。模型说“测试通过”不能替代原始执行记录。
5. 先用确定性验收判断补丁行为，再由不知道组别的评审者按冻结判据评估诊断和证据。重要争议由维护者复核原始记录，不让另一个模型的总分成为唯一依据。
6. 探索性试用可每组一次，但只能报告该次结果。发布效果比较建议每案例每组至少 3 次，并按案例配对报告；这个次数是起步成本约定，不是统计充分性保证。

清洁的对照组应不注入技能正文与描述；运行环境无法做到时，记录对照可见的技能目录信息。记录工具、上下文和推理设置差异，不能把基础模型变强当作 Skill 提升。

## 判据

逐案例、逐项标注 `通过 / 部分 / 未通过 / 不适用`，每个判断附输入、日志、代码或输出证据；不适用项不加入分母。

| 维度 | 观察什么 | 不应如何评分 |
| --- | --- | --- |
| 诊断正确性 | 找到失效位置与因果机制，排除必要的竞争假设 | 只因提到相关术语就算命中 |
| 证据与不确定性 | 区分观察、推断、未知；材料不足时不编造根因 | 奖励武断且碰巧猜中的答案 |
| 修复充分性 | 修复触发问题，并在变化输入下满足契约 | 只看异常消失或单个示例成功 |
| 行为保留 | 结果、权限、副作用、并行、状态隔离等适用约束不退化 | 把串行化、吞错误、丢字段当作默认修复 |
| 误报控制 | 正常反例不被归为故障，节点内部错误也能处理 | 认为报告更多风险就是更好 |
| 提问与范围控制 | 问题能区分假设，先自行读取已有证据 | 仅按问题数量少评分，或奖励八维问卷 |

效率单独记录：完成时间、模型 token/费用（若可用）、工具调用与补充材料轮次。在任务同样完成且环境可比时才比较；没有数据写 `null`，不猜测。

## 阻止发布的条件

当前拟定的维护门槛，不是已经得到实验支持的效果阈值：

- 格式、引用或确定性回归失败，测试被无说明地跳过，或者原先可复现的坏行为不再触发但原因未知。
- 在已有强制案例上引入新的错误根因、数据损失、权限扩大、重复外部副作用或未经业务允许的语义改变。
- 用编造的运行结果、伪造来源或未执行的 CI 支持效果宣传。
- 将开发集成绩写成保留集成绩，或将框架测试数量写成模型准确率。

若只改文档且未改变模型可见指令，运行结构检查即可；若改变 SKILL.md 或被引用指令，至少做受影响行为的前向试用，并保留旧案例回归。依赖版本更新时，先确认旧问题是否已被上游修复，再调整期望，不能直接删除变红的复现断言。

## 怎样报告结果

公开：案例数及家族数、来源与版本、各组每例重复次数、适用判据分母、逐项结果、关键误报/漏报、实际代码验收、执行环境，以及未测内容。关键失败单独列出，不能被平均分抵消。

当前项目不使用一个百分制总分。数据充分时可报告成对成功差异与不确定区间，同时展示每类失败；没有足够重复就只描述观察结果。两组都通过时应写“未观察到增益”。

运行记录的最小字段：

```json
{
  "kind": "model_behavior_eval",
  "skill_version": "版本或提交",
  "skill_tree_sha256": "含被引用文件的整体摘要",
  "case_id": "稳定案例 ID",
  "split": "development",
  "condition": "with_skill / without_skill / previous_version",
  "model": "实际模型版本",
  "reasoning_effort": "实际设置或 unknown",
  "tools_and_context": "允许访问的工具、材料与已知污染",
  "trial": 1,
  "input_and_oracle_hashes": {},
  "artifact_paths": [],
  "criteria_results": [],
  "critical_failures": [],
  "tokens": null,
  "cost": null,
  "elapsed_seconds": null,
  "limitations": []
}
```

示例字段是记录规范，不能直接作为已完成评测上传。首次历史试用没有采集完整模型版本和费用信息，历史摘要明确保留这个缺口。
