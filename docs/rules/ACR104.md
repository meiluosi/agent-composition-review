# ACR104 · 错误后部分写入

**级别**：high（轨迹检查）
**命令**：`acr trace <trace>`

## 症状

- 节点报错退出，但轨迹里它已经写入了部分状态，重试时拿到半成品。
- 失败重试后出现重复数据，或状态出现“半个完成”的不一致组合。
- 任务最终失败，但下游已经读到并消费了中间写入。

## 为什么发生

一个节点里可能有多步写操作。若中途抛错，前面已提交的更新是否保留取决于框架与实现；很多实现只在内存里返回 dict，但外部副作用已经发生，或者状态在异常前被旁路写入。重试从带有半成品的状态继续，就会叠加。

## acr 输出示例

```text
$ acr trace tests/fixtures/trace_parallel_writes.json
acr trace - tests/fixtures/trace_parallel_writes.json

  HIGH   ACR104  Error raised after partial state writes
    event seq 5
    Error raised after 2 state write(s) had already been applied. The failed run can leave partially updated state behind.
    evidence:
      - e3: node_end node='left' wrote 'b' (seq 3)
      - e4: node_end node='right' wrote 'b' (seq 4)
      - e5: error at seq 5 ("InvalidUpdateError: At key 'b': Can receive only one value per step.")
    fix: Wrap the step in error handling that records or rolls back partial writes; re-run from the last successful checkpoint.
    docs: docs/rules/ACR104.md

（同一条轨迹还会报告 ACR105 与 ACR103。）
```

## 最小修复

```python
def finalize(state: State) -> dict:
    try:
        receipt = store.commit(state["draft"])  # 一个原子提交点
    except Exception:
        store.rollback(state["draft"])          # 清理半成品
        return {"status": "failed"}             # 显式失败标记，不伪装完成
    return {"status": "completed", "receipt": receipt}
```

把“业务完成”收敛到一个可回滚的提交点；无法回滚的外部操作，用幂等键 + 发起前记录来避免重复。

## 验证

- 模拟异常，确认状态里不会出现“看似完成”的组合。
- 失败后重试，外部副作用只发生一次，清理逻辑可重入。
- 最终状态能区分 completed / failed / 未开始。

## 误报边界

- 框架的 checkpoint 语义本就保留“已成功的 step”，部分写入是预期的恢复点：需要看恢复逻辑是否清理了未完成部分。
- 报错发生在纯内存返回之前、且没有任何外部副作用：影响可能只是状态显示，不一定需要事务。
- 写入的键在错误后被后续节点覆盖，且业务可接受：仍需在报告里说明这个假设。
