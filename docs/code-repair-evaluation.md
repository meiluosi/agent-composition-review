# 自主建模与跨运行机制修复：复现说明

本轮评估从原始需求和代码自行建模、直接修改代码的能力。六个开发任务来自三个实际可执行机制：LangGraph 并行子图、SQLite 嵌套事务、asyncio 子任务生命周期。每个机制有故障版和正常版；它们是小型集成复现，不是三个生产系统或新的外部保留集。

## 对照条件

| 条件 | 原始代码、需求、smoke、结构格式 | 契约检查脚本 | v4 指导与按需参考 |
| --- | --- | --- | --- |
| A_basic | 相同 | 无 | 无 |
| B_tools | 相同 | 有 | 无 |
| C_v4 | 相同 | 有，与 B 相同 | 有 |

每组每例两次，36 次修复；随后每份结果进行一次新上下文的结构评审，最多另 36 次调用。没有提供当前任务的参考结构或修复答案；C 保留 v4 运行包自带的通用检索示例，它属于该组指导材料。共同要求交付 `model.json`，因此这并非自然触发实验；不能将差值解释为范畴论的整体效应。

实际原批次完成 30 次修复，6 次因额度限制中断；原 36 次评审也全部因额度限制失败。2026-10-04 另行冻结并完成 [31 次评审恢复](../evals/iterations/code-repair-2026-09-30/review-recovery-2026-10-04/PROTOCOL.md)，没有覆盖原记录或补跑代码。CLI 从 0.158.0-alpha.2.1 变为 0.160.0，精确模型服务快照仍未知。恢复评审包含一份中间模型，另五次缺少模型，不伪造结果。

首指标是所有适用行为验收通过，同时执行过程有效。故障修复、正常行为保持和正常源文件是否原样保留分别报告。辅助指标分开记录结构语法/引用有效和三项机制判据的盲评标签，不合并成总分。

**冻结后发现的题目限制**：异步预设正常例 c06 在“失败清理期间收到一次父取消”的交错下并不正常；事务预设正常例 c04 也漏掉了提交失败后的回滚。原调度与原评分保留，不能将对二者的必要修复解释为误改。额外探针、修订正常参考和发现过程见 [正常例审计](../evals/code_repair_followup/README.md)；补充结果必须另列，不覆盖冻结分数。正常保持仅能在 c02 上作有限解释。

## 冻结与证据

[分析计划](../evals/iterations/code-repair-2026-09-30/ANALYSIS_PLAN.md) 和 [冻结清单](../evals/iterations/code-repair-2026-09-30/manifest.json) 记录提示、任务、判据、代码、脚本、依赖版本、调度及哈希。每次尝试留下开始记录；中断、无效输出和超时不按结果补跑。原始服务日志留在本地忽略目录，整理后的提交代码、模型、补丁、命令审计和评分用于复核。

执行者只能看到当前任务材料，不能看到后置验收器、正常参考修复或维护者建模判据。后置验收在独立进程加载提交的 `app.py`：图检查最终状态、两处并行及实例隔离；事务检查提交可见性、批次原子性与调用者保存点；异步检查并行有序返回、原始异常、取消及工厂失败后的清理。公开 smoke 只覆盖一个简单输入。

结构评审看到原代码、提交代码、模型、需求、行为验收和预设判据，不能看到组名、指导文件或工具日志。它仍可能从产物风格猜到条件，所以只是部分盲评。相同请求模型的独立上下文也不等于独立的人类专家。维护者回读负面标签与代表性正面标签，保留原始判定。

## 复现

环境为 Python 3.12，安装 `requirements-eval.txt` 与 `requirements-benchmark.txt`。本机冻结的具体 Python、SQLite、LangGraph 及 CLI 版本在清单中；请求的模型别名并不保证未来服务权重完全不变。

无需模型调用的检查：

```sh
.venv/bin/python -m unittest evals.code_repair.test_fixtures evals.code_repair.test_protocol -v
.venv/bin/python scripts/analyze_code_repair.py publish
.venv/bin/python scripts/analyze_recovered_code_reviews.py
.venv/bin/python scripts/audit_code_repair_boundaries.py
.venv/bin/python scripts/render_code_repair_report.py
```

第二条在结果发布后，从记录中的源文件重新执行行为验收、检查模型引用和产物哈希，并重画图表。它不是用保存的分数假装重验，也不重新调用评审模型。记录中的历史错误文字可能随平台变化，只比较检查名称、数量和通过状态。

其余命令分别校验恢复评审、重放已审阅产物的事后探针、生成区分额度失败与行为结果的报告和图。原自动图的评审零值代表无有效评审，不是语义错误率；README 使用带有可用性说明的新图。完整 [结果](../evals/iterations/code-repair-2026-09-30/REPORT.md) 与 [维护者复核](../evals/iterations/code-repair-2026-09-30/CURATOR_REVIEW.md) 保留各层证据。

重新运行模型需要明确的新实验目录/冻结记录，不能覆盖此轮。维护者本轮的命令依次为 `run_code_repair_eval.py freeze`、`run_code_repair_eval.py run`、`review_code_models.py`、`analyze_code_repair.py import`；执行脚本会拒绝悄悄重跑已经开始却没有结束记录的尝试。

## 限制

只有三个家族，两个变体和重复并非独立系统样本。图表按固定 c01–c06 顺序累计，曲线不是训练过程，也不与以前的外部归因题拼接。聚类差值的 27 种重采样范围仅用于敏感性展示，不是可靠的总体置信区间。

本机执行和后置验收限制写入及网络，但不提供完整读取隔离；依赖路径可见。命令审计不能证明恶意代码没有越界读取。Linux CI 仅以进程和超时隔离，重验前需先审阅待执行产物。本轮目标是检验模型工程能力，不是研究恶意执行者的沙箱逃逸。

结构语法有效、评审认为覆盖判据和有限行为测试通过，分别证明不同范围的事实。它们都不能证明任意并发调度、无限输入域、因果关系或生产泛化。
