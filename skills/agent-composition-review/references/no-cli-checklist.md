# 无 CLI 降级检查单

当环境里没有安装 `acr`，或不允许执行命令时，不要假装“已扫描”。按下面 10 步人工审计，每一步都留下证据（文件、行号、日志、事件 ID）。

开头先写清楚：

> 未运行 `acr scan` / `acr trace`；以下为人工代码/日志审计，证据不足处已标注。

## 1. 冻结一次可复现的失败

- 记录：框架版本、输入、完整报错/错误输出、最小复现路径。
- 没有可复现失败时，先构造最小图；不要直接通读整个仓库。
- 证据：报错原文、版本号、复现命令。

## 2. 画出边界，而不是画整个架构

只标出与故障有关的四类边界：

- 父图 / 子图；
- 并行扇出 / 汇入；
- 节点 / 外部工具或副作用；
- checkpoint / retry / resume / cache。

证据：`add_node` / `add_edge` / `add_conditional_edges` 的行号。

## 3. 查状态 schema 与 reducer

- 故障键是否在 state schema 中声明？
- 是否用 `Annotated[..., reducer]`？reducer 是否可交换？
- 是否有多个写者会在同一 superstep 写同一个非 reducer 键？

危险信号：`At key 'x'` + 并行分支 + 该键没有 reducer。
证据：schema 行号、写该键的节点行号。

## 4. 查子图输出边界

- 子图是否声明 `output_schema`？
- 子图是否把完整父状态（含旧值）当补丁回传？
- 子图与父图是否共享同名状态键？

危险信号：`StateGraph(State)` 直接 `compile()` 后挂到父图，且父图另有分支写同一键。
参考：[ACR001 案例 #6446](../../../docs/atlas/lg-6446.md)、[ACR003 文档](../../../docs/rules/ACR003.md)。

## 5. 查并行写者

- 从 `START` 或同一节点扇出的分支，是否会落在同一 superstep？
- 每个分支是否写同一个单值键？
- 如果加 reducer，语义是否仍然正确（顺序、去重、合并规则）？

危险信号：两个分支都返回 `{"b": ...}`，`b` 是 `str`。
参考：[ACR002 文档](../../../docs/rules/ACR002.md)。

## 6. 查节点返回键

- 节点 return 的 dict 字面量里，每个键是否在 state schema 中？
- 类节点是否用了另一个 input schema，返回键没映射回父图？
- 下游读不到字段，是不是因为 LangGraph 在节点边界静默过滤了未声明键？

危险信号：`return {"note": ...}`，schema 只有 `{"x": int}`。
参考：[ACR007 案例 #8320](../../../docs/atlas/lg-8320.md)、[#2581](../../../docs/atlas/lg-2581.md)。

## 7. 查 cache / retry 与副作用

- `cache_policy` / `retry_policy` 是否包住了非幂等外部写（发消息、扣款、建单）？
- cache key 是否包含采样参数、输入版本、业务幂等键？
- retry 是否只覆盖可安全重放的操作？
- 多个图是否共享同一个 cache 对象？callable 是否有稳定身份？

危险信号：副作用节点上直接挂 cache/retry；cache 结果“太稳定”。
参考：[ACR004](../../../docs/rules/ACR004.md)、[ACR005](../../../docs/rules/ACR005.md)、[ACR008](../../../docs/rules/ACR008.md)。

## 8. 查 resume / checkpoint 边界

- resume 前哪些节点已经 `node_end` 且没有 interrupt？
- resume 后这些已完成节点是否又 `node_start`？
- 被 interrupt 的节点重启是预期行为，不要和“已完成节点重跑”混为一谈。
- 有 trace 时按事件序列核对；没有 trace 时只记录“需要日志”，不要猜。

危险信号：resume 后模型被调用两次、工具扣款两次。
参考：[ACR106 文档](../../../docs/rules/ACR106.md)、[#3875 负向控制](../../../docs/atlas/lg-3875.md)、[#9276 正向案例](../../../docs/atlas/lg-9276.md)。

## 9. 归因分级

把每个候选结论标成三类之一：

- **已证实**：能解释“单独跑正常、组合后坏”的完整因果链；
- **设计如此**：边界是有意的，当前行为可接受；
- **证据不足**：需要更多运行/日志/版本信息。

没有“已证实”证据时，不要进入修复；把“还需要什么证据”写清楚。

## 10. 最小修复 + 回归 + 报告

- 一次只改一个边界：`output_schema` / reducer / 幂等键 / cache key / 完成边界；
- 保留原有上下文读取和并行关系，不为了消错把并行改串行；
- 回归要覆盖：旧故障能复现、修复后不再出现、正常路径结果不变、重复执行不产生第二次外部效果；
- 报告用“结论 / 症状与复现 / 证据 / 根因 / 最小修复 / 验证 / 剩余风险”七段式。

参考：[最小修复模式](fix-patterns.md)、[病例索引](case-index.md)。
