# 首轮复盘与下一轮迭代

后续状态：本页提出的 v2 已完成 96 次四组开发消融，未达到预期；“全包稳定有害”的假设也未在复测中得到支持。见 [实测结果与迭代决定](ablation-findings.md)。以下保留实验前的分析，不将当时假设改写为已证实结论。

这是一份事后开发分析，不是新的效果评测。依据为首轮 144 次原始运行、冻结的输入及标签、公开预测表和当前 Skill。没有追加模型调用，没有修改首轮分数。统计可用 `python scripts/analyze_pilot_deltas.py` 重建，输出见 [分析记录](../evals/iterations/pilot-postmortem.json)。

## 先把下降拆开

首要指标在 Who&When 上从 18/36 降到 15/36，Pro 两组都是 19/36。Who&When 的净下降全部来自 Algorithm-Generated:50 和 :88：前者从三次中对两次变为全错，后者从对一次变为全错。其余 22 个任务的三次平均定位分数相同。

72 对回答中，65 对的 Agent、位置、类别三个归因字段全部相同。按同任务、同 trial 序号作描述性比较，位置得分为：33 对双方正确、34 对双方错误、1 对无 Skill 错/有 Skill 对、4 对反方向。trial 序号不是共享随机种子，不能把这些对比当作四次独立的因果证明。Pro 的 alfworld_alfagent_0288 有一次改善和一次退化，三次平均抵消。

输入 token 从 1,162,262 增至 1,626,928（约 +40.0%），输出从 18,938 增至 23,220（约 +22.6%）；这些是本轮完整材料注入的实际消耗，不代表正常按需加载的成本。更长输出没有带来定位收益。两组总体平均置信度均约 0.91，高于约一半的标签匹配率；这是事后发现的校准风险，不能把单条自报置信度当成已校准概率。

因此，当前可支持的结论是：**完整注入没有展示定位增益，增加了上下文成本，并在两个任务上出现了归因退化。** 不能推出所有架构场景都受损，也不能据此确定某一句指令是原因。

## 两个退化案例提供了什么证据

### Algorithm-Generated:50：实际错误与后续风险混在一起

在冻结源轨迹中，第 3 步使用不存在的 Excel 列名，第 4 步明确报 KeyError；第 7–8 步改用正确表头并成功读取。第 9 步提出下一段计算代码，轨迹没有它的执行结果。源标签指向第 3 步。

无 Skill 组两次选第 3 步，同时说明这个错误已经修复，最终失败原因仍不充分。有 Skill 组三次选第 9 步，关注分区行过滤与数据清洗，或最后一次尚未完成的交接。其回答也承认 NaN 分区行本身未必影响最小值计算，且没有末尾运行证据。

这里的可改进点是：不能把“确实有一个不准确的代码注释/潜在风险”提升为“已导致最终失败”。需要同时保留已观察错误、恢复状态和未执行风险，按用户要求的归因目标排序。

这也暴露了数据解释限制：源标签选了已在可见轨迹中恢复的错误，单凭当前材料不足以验证它怎样导致最终失败。但这不证明源标签错误，更不能事后改标签给 Skill 加分。Who&When 原论文同样以最早的决定性错误为目标，并非笼统要求找第一个异常；它也报告了人工归因中的不确定性。[原论文，第 2、3 节](https://arxiv.org/pdf/2505.00212)

### Algorithm-Generated:88：发现了依赖问题，却没有追到最早引入者

第 0 步已明确文件缺失，却仍给出依赖该文件的代码；第 1 步先遇到缩进错误。第 2 步修复缩进，但继续假设文件存在，第 3 步报 FileNotFoundError。源标签指向第 0 步。

两组多数回答都发现“文件没有准备好”和“执行终端不能完成文字中的下载请求”。无 Skill 组有一次追到第 0 步；有 Skill 组三次都选择第 2 步。

这个案例没有显示 Skill 未理解契约，反而显示理解契约之后仍会把后续重试者当作最早责任主体。需要区分错误引入、传播、暴露和修复位置；“修这里可以继续”不足以证明“这里就是最早根因”。

两例来源均为冻结的 [Who&When 数据版本](https://huggingface.co/datasets/Kevin355/Who_and_When/tree/59b9fcba1aaed7bbf206b5f4d3c68b8face2f49c)。上述是原始轨迹与回答的复盘，不是重放实验，不据此作已证实的指令因果归因。

## Skill 和执行器各有什么问题

| 层面 | 已观察的事实 | 当前判断与可证伪假设 |
| --- | --- | --- |
| 加载方式 | 每次注入正文和三个完整参考文件；旧版正文 2,458 字符，全包 9,809 字符 | 正文原本要求按症状阅读。全量注入可能引入干扰；要比较旧版正文与旧版全包才能检验 |
| 适用范围 | 原 Skill 包含取证、询问、运行测试、修复、架构审查；实验只有静态轨迹与单个 JSON 回答 | 上轮实际测的是受限日志归因，未测自动触发、主动提问或代码修复；不能外推整个 Skill 的好坏 |
| 诊断顺序 | 异常入口、维度表和交付示例反复强调边界；“也检查节点”主要出现在后文 | 可能形成先找交接故事的倾向；两例与该假设相容，但不足以证明由这段文字导致 |
| 证据状态 | 区分事实和推断已有原则，但没有明确表示错误引入、恢复和未执行风险 | #50 支持增加这一有限区分；不应添加“总选最早异常”这种反向过拟合规则 |
| 因果来源 | 已要求寻找最早偏差，但未明确分开引入者、传播者、观察者与修复者 | #88 支持保留事件来源和传播链，避免只定位最容易修的位置 |
| 评价目标 | 两个数据集共用决定性错误提示词，强制单个位置；无弃答通道 | 不充分证据与“必须报位置”有张力。新实验需把标签匹配和证据质量分开；不能改变旧成绩 |
| 理论模块 | Markov 复制、近似交换、胶合均全量注入，但退化案例没有直接涉及这些机制 | 尚无证据说明这些理论错误或有用。应由具体症状触发，并在对应任务上验证 |

Pro 的注入标签与一般排障也应区分：知道某处被替换，不等于仅凭展示的失败轨迹就能唯一恢复该标签。其官方任务仍是决定性错误定位；本项目不应把注入位置、第一次局部错误和当前阻塞混成一个语义类型。[官方任务及生成流程](https://whowhenpro.github.io/)

本轮两组都错的案例也不能忽略。例如 math_debate_0084 两组都定位到第 0 轮的几何推理，标签为第 1 轮协调错误；这是错误传播与恢复机会的分界问题，不能靠增加架构术语解决。下一轮应分别记录它们，而非只展示两个有利于修改的案例。

## 继续采用范畴论，但改变落点

保留组合思想作为接口与信息保持的设计约束。用它检查诊断流程自身：

```text
原始轨迹
  → 带来源、事件位置、证据状态的事实
  → 带引入/传播/恢复关系的候选解释
  → 针对明确归因目标的判断
  → 与该判断对应的验证或修复
```

这些是工程契约，不宣称已经构造出某个形式范畴或证明正确性。每一阶段需要明确输入、允许的变换、产物和未知分支；箭头可连接只是起点。

| 组合思想 | 下一版具体行为 | 可观察的验证 |
| --- | --- | --- |
| 对象与态射的类型 | 把 `ObservedFailure`、`RecoveredError`、`SuspectedRisk` 和 `Diagnosis<Target>` 分开 | 未执行代码不被当作已发生失败；不同归因目标不被静默互换 |
| 组合中保持语义 | 候选解释始终引用原始事件与来源 | 后续重试不覆盖错误最初引入位置；摘要仍能回到日志 |
| 行为等价与近似比较 | 对同一原始事件的无损编号/排版变换，映回后的判断应相容 | 编号重排不改变实际指向；缺失关键内容则应改变不确定性，而非假装等价 |
| 随机组合 | 把多个诊断视为有共同输入和相关性的样本 | 不用多数票自动升级为证据；记录真实调用与共享材料 |
| 胶合的工程启发 | 不同领域检查共享事件 ID、定义、证据状态和冲突规则 | 合并保留不相容结论；不让总结覆盖分歧，也不声称两两一致保证全局正确 |

Markov 范畴为随机映射及组合提供数学语言，复制一个结果与独立生成多个结果不是同一过程；但它本身不是日志根因识别算法。[Fritz 的定义与复制讨论](https://tobiasfritz.science/2020/markov_cats.pdf) 工程中的来源追踪、契约测试与领域验证仍需独立实现。范畴论不应被写成“凡失败必在边上”的归因先验。

## 是否需要组合多个 Skill

可以组合能力，但现在先不增加常驻 Skill 或多 Agent 调用。建议先在一个 Skill 内形成：轻量入口、证据与候选组织、按需领域检查、归因选择、验证交付。没有条件触发的专门机制，不加载对应参考文件。

真正拆为独立 Skill 时，边界应是可复用的工作：例如代码执行验证、数据语义检查、采样调用机制检查。每个子检查交付 `事件引用 + 观察/推断 + 违反的明确要求 + 反证/未知`。归因环节保留这些类型；不能把子 Skill 的建议当成事实。最初可在同一模型上下文完成，不默认让每一步成为一次额外模型调用。

“基础模型 + 更多 Skill”没有单调变好的保证。先证明按需模块比简洁入口增加了可验证收益，再承担更多 token、接口冲突和调度成本。
