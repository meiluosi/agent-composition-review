# 接口、语义与契约

适用于接口交接、架构审查和组件替换。先区分三个视图：架构说明连接方式；行为说明组件实际做什么；要求说明允许哪些结果。接线图可以建立连接的形式模型，具体行为和契约仍需要单独解释。

## 最小模型

为关键步骤记录输入类型、输出类型、状态、效应、前置假设和行为保证。类型包括结构及业务含义：单位、时区、版本、来源、覆盖范围、快照/补丁/命令的区别。字符串作为载体并非错误；错误在于消费者需要的区别没有表达或检查。

普通串联可以将接口类型作为对象、计算作为态射；必须说明恒等操作、组合及其规律。开放系统的接线图还有不同建模方式，不强行把所有节点都叫对象、所有边都叫态射。幺半积表示所选模型的并置，不自动证明生产环境中并发互不干扰。

## 组合义务

若组件 f 在前置条件 P 下保证 Q，组件 g 需要 R，应验证 Q 是否蕴含 R，并检查它们之间是否存在改变状态或假设的操作。仅有 schema 相同不够。局部性质要推出整体性质，必须给出相应组合规则；例如读写资源、错误分支、终止和业务约束不能隐藏在纯输入输出模型外。

替换组件需要明确行为观察范围及精化方向。常见要求是在原来允许的输入上不增加调用方负担，并满足原保证；具体契约可能另有约定，不把这一经验当作所有契约模型的统一定义。

**反例**：`SearchResult=[]` 可能是成功空结果，也可能是超时的兜底。即使确实成功且为空，也不能在检索覆盖范围未知时推出“记录不存在”。建议区分 Found、Empty、Partial、Failed，并约束下游陈述。

**验证**：正常输入、假设不满足、异常分支各取有区分力的例子；执行生产者到消费者的整条交接，检查要求而不只检查解析成功。对于重构，函子保持恒等与组合的定义不能直接推出任意业务不变量被保持。

依据：[Bakirtzis 等，架构、行为与契约的范畴语义](https://arxiv.org/abs/2010.08003)。该工作研究信息物理系统；上面的 Agent 检查流程是工程应用，尚未因此获得形式保证。
