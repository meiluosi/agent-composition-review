# ACR009 · retry_policy 节点内调用多个子图

**级别**：medium（静态检查，构图层）
**命令**：`acr scan <path>`

## 症状

- 一个节点里依次调用 `research.invoke(...)`、`review.invoke(...)`；节点配置了 `retry_policy`。
- 第一次尝试在两次调用之间失败；恢复后，本该执行 `review`，却拿到了 `research` 的结果。
- 更一般地：重试/恢复后第二个子图“没有真正运行”，直接命中第一个子图的 checkpoint。

## 为什么发生

子图的 checkpoint 命名空间包含父节点 task 的位置/计数信息。节点启用 `retry_policy` 后，重试会重新进入同一个节点；如果节点内已经调用过一个子图，第二个子图可能继承/复用前一个子图的命名空间。恢复时它看到已有 checkpoint，于是直接返回旧结果。

这是**重试 × 子图身份**的组合问题，不是单纯的“重试写重复”或“子图输出越界”。

## acr 输出示例

```text
$ acr scan app/graph.py
app/graph.py:47: medium ACR009
  Node 'node' enables retry_policy while invoking multiple subgraphs ('research', 'review').
  After a retry or resume, a later subgraph can land in the first subgraph's checkpoint namespace...
  evidence:
    - node 'node' registered with retry_policy at line 47
    - node function invokes multiple subgraph-like targets: 'research', 'review'
  fix: Avoid multiple subgraph invokes inside one retried node; split them into separate nodes...
  docs: docs/rules/ACR009.md
```

## 最小修复

把一个节点拆成两个，让每个重试单元只负责一个子图：

```python
graph.add_node("research", research_node, retry_policy=RetryPolicy())
graph.add_node("review", review_node, retry_policy=RetryPolicy())
```

如果确实要在同一节点内调用多个子图，给每个子图调用传入独立的 checkpoint/namespace，并在恢复测试里断言“第二个子图真的执行了”。

## 误报边界

- 只报同时满足“节点有 `retry_policy`”和“函数体内调用 2 个以上不同 target 的 `.invoke/.ainvoke`”的静态可见情况。
- 只调用一个子图、没有 retry、或调用的不是子图（普通 runnable/tool）时不报。
- 新版 LangGraph 可能修复了该命名空间行为；规则描述的是“这个结构在旧版本上有风险”，不是断言所有版本都错。升级后应结合版本与回归测试判断。
