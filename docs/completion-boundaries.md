# 从完成边界继续推进组合框架

这一轮的两个额外反例指向同一个具体缺口：我们最初检查了动作主体，却没有完整检查“这个组合什么时候才算结束”。这首先是评测设计错误：参考实现通过了有限验收，被过早当成了符合完整文字要求的正常实现。不能把模型发现参考实现的遗漏计为误报。

证据与修订参考见 [冻结后正常例审计](../evals/code_repair_followup/README.md)。这些结论来自真实 SQLite 和 asyncio 的本地执行；不是生产事故统计，也没有证明新指令能够提升模型成绩。

## 对应到组合框架

| 机制 | 被混同的两个事实 | 应保留的组合条件 | 可区分的执行检查 |
| --- | --- | --- | --- |
| 图的子图边界 | 能读取字段 / 有权提交字段 | 读上下文与写入所有权分别声明 | 父、子两处并行均保留；子图只输出自己负责的更新 |
| 事务工具 | INSERT 成功 / 批次已成功完成 | 提交与撤销都属于工具的效果范围；外层事务归调用者 | 插入成功后制造提交失败，再复用连接检查可见性 |
| 异步工具组 | 首个错误已传播 / 所有自建子任务已退出 | 退出前清理完成；取消只针对自己拥有的子任务 | 让一个子任务失败，兄弟开始清理后再取消父调用 |

还需要区分“Task 已终止”和“业务清理已完成”。补充探针发现，一份修复会再次取消已经在清理的子任务：最终没有未完成 Task，但清理效果并未发生。若观察模型只保留任务终态，就丢掉了验证业务清理所需的信息；应增加清理效果证据或保留未知，不能把更粗的状态当作更强的不变量。

范畴论在这里提供的是建模纪律：组合的对象、态射和可观察行为必须足够明确，才能讨论组合后保持什么性质。带状态与效应的计算、并行组合、契约的假设与保证都与这些问题相关。但仅写出输入输出类型、Monad 或张量符号，不会自动证明取消、锁或提交语义正确。具体代数结构及其定律需要另行定义和验证。

一个动作的工程描述至少要能区分：开始前的资源归属、主体执行、成功完成、失败清理，以及退出后的可观察状态。这里不是要求所有任务都生成同样的五层 JSON；短任务也可以在代码和测试中明确这些事实。

## 有证据支持的追问

1. **完成条件是什么？** 返回成功是否意味着效果已经提交？抛出异常是否意味着后台工作已经停止？
2. **谁拥有剩余资源？** 当前函数创建的事务、任务或更新，与调用者原有资源是否区分？结束时应释放什么、保留什么？
3. **完成和清理还能失败吗？** 提交失败是否进入撤销路径？清理期间的新取消是否会打断清理？保留哪个异常需要明确约定。
4. **保证依赖哪些环境假设？** 例如 SQLite 被触发器或 I/O 错误强制回滚整个事务时，局部保存点不可能无条件保护所有外层状态。应说明保证适用范围，不能填一个“原子性成立”字段就略过条件。
5. **验收是否覆盖阶段之间的交错？** 分别测试“子任务失败”和“父取消”，不等于测试“失败处理期间父取消”。应使用门闩等控制顺序，使反例可以稳定复现。

上述追问与现有 [运行语义参考](../candidates/v4/agent-composition-review/references/effects.md) 的所有权、取消和未完成效果方向一致。当前证据支持补全案例与检查条件，尚不能单凭它认定 v4 缺少这些概念，也不能证明再增加一段文字就能提高成绩。

## 对后续验证的约束

原冻结分数保留；额外探针单列。正常参考应同时通过正常路径与相关失败路径的验收，并明确环境假设。模型判为违规而参考标签判为正常时，应审查实际反例，不能直接按标签否定模型。

下一轮若测试这些追问的增量，应先使用修订正常参考和新的边界任务，冻结判据，再比较原指导与候选指导。本轮发现过的交错已是开发材料，不能改名成为未见保留集。无需因为内容增多而拆出多个 Skill；它们仍围绕同一个诊断任务、同一条修复与验收流程。
