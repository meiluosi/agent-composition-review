# Agent 组合架构审查

将问题落实为可检查的行为与要求。节点内部错误、交接错误和环境问题都可以成为原因；范畴论用于明确组合条件，不预先决定故障在哪里。

## 核心流程

1. **确定判断对象**：异常排查明确是在问局部错误、决定性原因还是当前阻塞；架构审查明确业务链路和要求；重构验证明确共同输入、可观察行为与容差。沿用用户或基准的定义，歧义影响结论时分别列出，不擅自替换目标。
2. **建立最小模型**：分别记录架构（连接与共享资源）、行为（实际执行、状态、效应）、要求（假设和保证）。先读实际代码与运行记录。没有记录的步骤保持未知，不能补写执行结果。
3. **保留可追溯候选**：对有争议的发现记录原事件 ID、违反的要求、证据状态、恢复证据及反证。计划、执行和结果不可互换；历史错误即使恢复也仍发生过，已恢复本身又不证明对最终结果无影响。日志包装角色、实际动作主体、堆栈组件分别保留。
4. **检查组合义务**：上游保证是否满足下游假设，状态和效应是否被遗漏，推断经过交接后是否变成了事实？按下表读取相关模块。优先执行能区分候选的最小检查；无法验证因果时给出候选与未知，不能把时间先后当作干预证据。
5. **有可运行系统时闭环**：将实际动作、状态、依赖和要求映射成可检查结构，从结构生成测试，执行后验收。不要把违规动作、暴露观察、因果候选和修复位置合并成一个“错误点”。参照执行模块；先验证行为，再整理报告。
6. **完成任务**：给出结论、原始证据、适用要求、最小修复和实际验证结果。已授权修复就完成修复及验收。正常链路可以报告符合已检查契约；证据不足不等同于发现故障。不要因格式整理而推迟可以完成的工作。

## 按问题读取

| 情况 | 参考 |
| --- | --- |
| 有代码或轨迹，需生成测试、回放或验收修复 | [结构与执行](references/executable-contracts.md) |
| 接口、语义、组件替换或架构建模 | [接口与契约](references/contracts.md) |
| 状态、失败、重试、并发、反馈、取消 | [运行语义](references/effects.md) |
| 日志归因、相互矛盾的证据、恢复、摘要失真 | [证据记录](references/evidence.md) |
| 缓存、多次采样、根因或反事实判断 | [随机与因果](references/probability-causality.md) |
| 多智能体交接、共享定义或合并 | [局部与整体](references/gluing.md) |
| 路径优化、重构容差、成本或误差传播 | [定量验证](references/quantitative.md) |

这些模块可组合使用，不要求全部读取或增加 Agent。理论依据和适用前提随模块给出；新增定理或版本特定行为时再核验来源。

复杂诊断可使用证据模块中的 JSON 记录，并运行 `python3 scripts/check_evidence.py RECORD.json` 检查引用和状态一致性。短问题直接在回答中保留必要证据即可；程序通过不代表事实真实或根因已证实。

组合合法、类型匹配、观察到某次成功，都不能单独证明业务正确或线上效果。没有明确度量与代表性数据，不给架构主观总分，也不因使用数学术语声称形式化证明。

可改造的起点：[检索结构模板](assets/retrieval.model.json)。它仅示范有限契约，不是所有 Agent 的统一类型系统。
