# Agent 组合架构审查

把异常转化为可验证的问题：这是什么数据，生产者保证什么，消费者假设什么，数据经过组合后哪些性质发生了变化？以真实链路和边界证据判断架构，给出最小修复和验证办法。

## 选择工作方式

- **异常排查**：从一次失败运行及相近成功运行切入，追踪第一个违背契约的边界，再追查上游原因。避免一开始遍历所有架构问题。
- **架构审查**：选取关键业务链路，覆盖正常、失败、重试和适用的并行分支，检查下列八个维度。区分未发现问题、证据不足和不适用。
- **重构验证**：明确新旧路径的共同输入、可观察结果、外部副作用和容许差异，检查行为是否按约定保留。

用户只要求诊断时提供诊断；已经授权修复时继续完成相关修复和验证。不要把架构审查扩展成无关重写，也不要为使用此技能强制启用多智能体。

## 建立最小事实底稿

先读已有代码、接口定义、提示词中的输入输出约定、测试、架构图和可用运行记录。缺少什么就标注什么，不用想象补齐系统。

记录目标行为、实际行为、影响、输入与相关版本。将关键路径写成简短链路或图，并标注数据、控制流及隐藏依赖：记忆、缓存、会话、随机性、权限、外部服务。静态函数签名不能代替真实运行行为。

对关键交接记录：`生产者 → 数据及状态 → 消费者 → 期望契约 → 实际证据`。存在循环时记录退出条件、重试预算和状态更新位置。不要仅凭图复杂或节点数量判断好坏。

缺失信息确实影响判断时，询问最能区分当前假设的少量问题，并说明答案将改变什么结论；能从项目中找到的内容先自行查找。只有高层描述时，交付假设、风险和验证方案，不宣称已定位根因。

## 八个审查维度

这些维度是本技能的工程组织方式，不是对某本书章节或原则数量的复述。

| 维度 | 关键提问 | 需要得到的证据或产物 |
| --- | --- | --- |
| 1. 组合路径 | 真实执行经过哪些步骤？哪条边首先偏离预期？ | 失败链路及与成功链路的差异 |
| 2. 类型与语义 | 上游实际输出是否满足下游前置条件？相同字段是否代表相同含义？ | 结构、业务语义、单位、来源、版本、有效期的契约 |
| 3. 状态与副作用 | 输出依赖什么隐藏状态？失败、重试、取消、并行会改变什么？ | 状态转换、错误分支、幂等范围和外部操作记录 |
| 4. 不变量与预算 | 哪个性质必须沿全链路保持？在哪里建立、传递、检查或丢失？ | 可断言的性质；分别列出可累计的成本与延迟预算 |
| 5. 近似交换与放大 | 两条本应等价的路径差多少？这点差异经过下游会造成什么后果？ | 明确比较口径的路径对照、局部差异和端到端影响 |
| 6. 复制、采样与缓存 | 需要的是复制一个结果，还是重新采样？投票中有几次真实生成？ | 缓存位置、键、命中记录和独立生成调用的证据 |
| 7. 多智能体胶合 | 子任务共同涉及什么？共享定义、版本和冲突处理是否在分发前明确？ | 重叠契约、覆盖检查、冲突与全局约束验证 |
| 8. 可执行验证与重构 | 该判断如何被证伪？修复如何证明有效？哪些行为必须保留？ | 最小反例、测试判据、新旧路径比较和剩余风险 |

排查具体边界时读 [边界契约与定位问题](references/boundary-contracts.md)。涉及路径替换、误差传播、采样缓存或多智能体合并时，按相关小节读 [高级组合模式](references/advanced-composition.md)，不必每次加载全部内容。

## 从怀疑到发现

针对最早的异常边界提出少量竞争假设：生产者违约、消费者误读、适配丢失信息，或状态/缓存/调度改变执行语义。优先选择能区分假设的检查：实际 payload、错误状态、调用次数、相同输入的路径对照。

每条发现都连接完整因果链：**触发条件 → 边界证据 → 被破坏的契约或性质 → 业务后果 → 最小修复 → 验证判据**。标注“已证实 / 有依据的怀疑 / 待验证”，并单独说明影响程度，避免把高影响当作高置信度。

验证时使用项目已有测试方式和隔离替身。不要通过重放真实支付、发送或删除操作来确认重复副作用。对于随机输出，使用任务级评价、分布比较或多次试验，不用单次文本一致性冒充正确性。

可进入 CI 的结论必须明确输入、预期行为或判定器、容许差异和失败条件；阈值来自业务要求或已说明的基线。缺少真实系统、数据或测试环境时给出测试方案，并标注未执行，不声称已经可运行或已通过 CI。

## 交付与判断边界

先给出影响最大的结论，再展示少量有证据的发现、待验证问题和下一步。使用 [输出与验证范式](references/review-output.md) 中与任务规模相称的结构；单个异常不需要完整评估表。没有明确权重和样本时不输出任意百分制总分。

把类型/变换作为范畴论启发的模型，把副作用、随机性和上下文纳入解释。结合律改变的是分组，不是执行顺序；并行化、重试或缓存都需要额外证明条件。

结构合法不能证明语义正确；局部正确不能自动推出组合正确；缓存不必然有害；重叠一致不自动证明全局可合并。不能因为使用了范畴论术语就声称获得数学证明、线上效果保证或自动化验证。

本技能受到用户提供的《组合智能》原则摘要与三个进阶概念启发。没有该书全文，不补造其定义、公式、章节内容或“七种重构模式”。数学出处与工程推导的边界见高级组合参考。

# 高级组合模式

按症状选读：路径优化或线上差异读第一节，多次采样或缓存读第二节，多智能体分工合并读第三节。以下工程方法是本技能的推导，不声称复现《组合智能》相关章节。

## 1. 近似交换与误差放大

### 从两条路径开始

找出具有相同输入和可比较输出的两条路径 `P, Q: X → Y`。例如原流程与压缩流程、工具结果与其适配后的等价表示。若用交换方图表达，则写清两条复合路径分别是什么，不要求无关步骤可互换。

先明确评价对象与距离 `d_Y`：结构差异、金额差异、证据支持率、动作分歧率或输出分布。语义相似度只能作适用范围内的代理指标，不能替代业务正确性。

对相同输入比较 `P(x)` 与 `Q(x)`，再比较下游 `h(P(x))` 与 `h(Q(x))`。记录局部偏差和最终影响，尤其检查阈值、路由、权限判断、排序及循环附近的差异。使用代表性正常样本和边界样本；若要推断线上表现，需要流量分布、版本和时间范围的依据。

### 什么时候可以写放大系数

当两个空间具有明确距离，且下游在指定范围满足 Lipschitz 条件：

```text
d_Z(h(y), h(y')) ≤ L · d_Y(y, y')
```

才能由局部偏差不超过 ε 推出最终偏差不超过 `L·ε`。串行多步在各步距离及适用范围兼容时，可累乘各步上界。有限样本上的最大观测比值只是经验敏感度，不能冒充全局上界；局部距离为零时不能直接做除法。

离散阈值可能不存在有限的全局 Lipschitz 常数。此时直接检查动作翻转率和后果。例如两条路径输出分数 0.79 与 0.81，虽然只差 0.02，在阈值 0.80 处却可能触发不同操作；这是合成示例，不是推荐阈值。

随机系统应比较输出分布或任务指标，说明采样方法和不确定性。使用总变差距离时，同一个 Markov 后处理核不会放大该距离；因此不要把“下游放大”宣称为所有距离下都成立。动作损失、选择偏差、重复调用与反馈应按各自模型分析。

**最小验证**：冻结输入及相关上下文，在隔离环境运行 P/Q，分别记录局部指标与端到端业务指标；用真实业务容许范围决定是否通过。没有合理指标时先交付定性风险和测量方案。

**修复方向**：保留关键字段、把损失性的转换后移、在敏感边界重新校验、限制反馈或调整容差。不要仅凭局部文本“看起来一样”接受重构。

## 2. Markov 范畴中的复制与缓存

在标准随机核模型中，对随机步骤 `f: X → Y`，以下两种过程一般有不同的联合分布：

```text
copy_Y ∘ f                 生成一次，再复制结果
(f ⊗ f) ∘ copy_X           复制输入，再分别独立生成
```

复制操作对一般随机态射不满足这种自然性；在 Markov 范畴中，保持复制是确定性态射的定义条件。工程上必须检查具体实现是否真的提供了所假设的随机性和独立性。[依据：Tobias Fritz，Markov categories，确定性与复制](https://tobiasfritz.science/2020/markov_cats.pdf)

简单反例：抛一次公平硬币后复制，仅产生 HH/TT，各 1/2；独立抛两次产生 HH/HT/TH/TT，各 1/4。单个输出的边缘分布相同，联合分布不同。

### 要识别的故障

用户希望多次生成候选答案后聚合，但系统按相同 prompt 缓存完整生成结果。后续调用命中同一结果，却被当作多票证据。这个缓存将重新采样替换成了复制，破坏了预期的采样过程。Self-consistency 原始方法依赖采样多条推理路径并聚合答案；这里关注的是它的调用与聚合机制。[依据：Self-Consistency 论文](https://arxiv.org/abs/2203.11171)

检查并区分：

- 缓存对象是确定性的解析结果、输入前缀计算、检索快照，还是一次随机生成的最终结果？前缀缓存本身不等于复用完整生成结果。
- 实际发起了几次底层生成？哪些请求命中了同一个缓存产物？有没有请求合并或共享随机种子？
- 多次生成共享了哪些记忆、上下文和中间结论？“不同 Agent”或“不同请求 ID”不证明独立。
- 聚合器是否把相同来源的复制品误计为独立证据？输出相同也不证明来自复制，需要调用轨迹验证。

**最小验证**：以可记录调用次数并产生预设不同候选的 stub 替代生成器；对声明需要重新采样的 N 次请求检查真实调用与缓存来源，再检查聚合是否错误地放大重复产物的票数。不要要求真实模型每次文本都不同。stub 只能验证调用机制，不能证明真实生成的统计独立性或业务收益。

**修复方向**：需要新样本的路径绕过完整结果缓存，或显式设计采样会话、样本身份与重放语义。采样序号进入缓存键只用于区分样本，不能证明独立；仍需检查实际随机源和共享状态。确定性预处理可继续缓存。若只是原样展示或恢复同一次采样，复用结果可以符合契约。

## 3. 层的胶合条件与多智能体交接

这里的“层”指 sheaf，不是神经网络层。数学上的胶合条件涉及覆盖、局部截面及其限制：局部截面在重叠区域一致时，在满足层公理的结构中存在唯一的全局截面。[依据：Stacks Project，Sheaves，Definition 6.7.1](https://stacks.math.columbia.edu/tag/006S)

工程启发是：**先声明重叠区，再分发；先验证兼容性，再合并。** 不能仅凭任务切分就断言系统形成了层，也不能仅凭两两一致保证业务上的全局解存在。

分发之前，为有共享依赖的子任务明确：

| 项目 | 要交付的约定 |
| --- | --- |
| 覆盖 | 总目标包含哪些要求，分别由谁负责，哪些尚未覆盖 |
| 重叠 | 共同实体、接口、字段、时间范围、共享资源与假设 |
| 比较口径 | 从各产物提取哪些共享字段，用什么单位、版本和语义比较 |
| 所有权 | 谁决定共享定义；变更如何通知其他依赖方 |
| 合并 | 验证器、冲突裁决方式、需要重做的条件和合并负责人 |

示例：前后端 Agent 共同涉及支付金额时，先声明 `amount_minor`、`currency`、舍入规则和接口版本。仅约定字段 `amount: number` 不足以保证兼容。

合并时先比较重叠契约，再检查整体覆盖和全局约束。若使用不同局部命名或单位，检查转换在三方及更多交接中的一致性。不要让总结 Agent 用流畅文字掩盖不兼容的产物。

两两兼容仍可能全局失败：三项任务各消耗 4 单位预算，总预算 10；任意两项都不超预算，但三项总和为 12。这是独立的全局约束，需要在合并时检查。

**最小验证**：对共享字段/接口提取规范化表示，注入一个单位或版本冲突，确认合并不会静默接受；再检查至少一个与项目有关的整体约束。冲突可按已有规则转换、裁决或返工，不默认要求人来批准每次合并。

## 出处与适用范围

上述数学定义链接到一手资料；缓存诊断、多智能体分发约定和测试设计是本技能的工程应用，不是数学文献对 Agent 的直接保证。近似交换部分的误差界由写明的距离与 Lipschitz 假设推出，未核验用户所述书籍的专门定义，也不引用其公式。使用现有参考即可完成一般诊断，无须每次重新联网；需要新增定理、精确引文或版本特定行为时再核验。

# 边界契约与定位问题

在工具调用、检索、记忆、路由、解析和任务交接处使用。沿异常链路选择相关问题，不把整份清单变成用户问卷。

## 数据到底是什么

区分三层约束：

| 层次 | 核心问题 | 常见反例 |
| --- | --- | --- |
| 结构 | 字段、可空性、枚举和返回分支是什么？ | 工具返回对象，适配层先转字符串，再由模型猜结构 |
| 语义 | 字段代表什么实体、单位、时间范围和知识状态？ | 同为 number，却将分当元；同为文本，却将模型摘要当原始证据 |
| 行为 | 正常、空、部分成功和失败如何区分？前置与后置条件是什么？ | 捕获超时后返回空列表，下游宣称“记录不存在” |

字符串适合承载自然语言。仅当下游需要依赖某种区别时，才把区别显式化；不要为每段文字制造没有验证价值的类型。JSON、Pydantic 或类型注解只是表达工具，需要对应解析、校验与错误处理。

涉及实体时确认身份域，例如 `CustomerId` 与 `AccountId`。涉及知识时确认来源、引用、观测时间、有效期、事实与推断的区别。涉及用户输入、检索内容或工具输出时检查数据是否被意外提升为控制指令。

## 一个交接契约应说明什么

按需要记录，未知项标注未知：

```text
边界：生产者 → 适配/序列化 → 消费者
输入：结构、业务含义、前置条件
输出：成功 / 无结果 / 部分成功 / 失败的表达
保证：消费者可以依赖哪些性质
依赖：状态、身份、权限、版本、随机性、时效
副作用：改变什么，操作身份如何识别，重试后应如何表现
不变量：哪些信息或限制必须跨过这个边界
证据：代码位置、契约定义、脱敏运行记录、测试
```

示例契约：

```text
SearchResult =
  Found(items: 非空 Evidence 列表)
  | Empty(scope, completed_at)
  | Partial(items, missing_sources, reason)
  | Failed(kind, retryable)

Evidence = {source_id, source_version, observed_at, content}
```

此处是语言无关的示例，应按业务裁剪。即使完整检索返回 `Empty`，通常也只支持“本次在指定范围未命中”；除非已证明数据源完整且查询完备，不可直接推出事实不存在。部分结果可以在契约允许时使用，但须保留不完整状态。

## 沿异常链路追问

1. 实际输入输出与哪条契约冲突？有运行证据，还是只看到静态代码？
2. 最早出现差异的位置是哪里？如果这里输入正确，输出是否仍错误？
3. 生产者保证的条件足以满足消费者需要吗？隐式转换丢了哪些字段、标签或来源？
4. 消费者有没有把 `unknown`、`empty`、`failed`、`false` 混为一谈？
5. 相同请求是否处在同一会话、记忆版本、权限和缓存状态下？
6. 成功和失败运行的最小差异是什么？哪次检查最能排除其中一个原因？

若边界契约已满足但业务仍失败，继续进入节点内部检查模型能力、检索质量、算法或依赖服务；“关注边界”不是预先断言根因一定在边上。

## 状态、循环与副作用

- **重试**：重试的是同一逻辑操作还是新操作？超时是否可能发生在远端已成功之后？幂等键覆盖哪个实体、操作和时间范围？
- **记忆**：写入的是事实、假设还是暂定计划？能否保留来源与有效期？读后更新是否有版本冲突？
- **并发**：是否读写相同资源？执行次序会改变结果吗？取消后是否仍有晚到写入？
- **循环**：每轮推进了什么状态？退出条件、最大尝试次数和总预算是否一致？
- **权限**：路由、缓存复用和工具执行是否仍受同一有效授权约束？只检查与该链路实际相关的权限。

把步骤看成 `输入 × 状态 → 结果 × 新状态`，并记录可能的外部操作，有助于暴露隐藏依赖。这是分析记法，不要求重写整个代码库。

## 三个已运行验证的边界模式

- **快照与补丁**：确认组件返回的是完整状态、局部更新还是操作命令。即使叶节点只修改自己的字段，封装后的子图也可能返回完整快照；当下游按返回字段执行更新时，只读透传字段会变成意外写入。分别记录可读字段与有权写入的字段，观察封装后的真实输出。若不存在合法共同写入语义，不要靠任意 reducer 压住冲突。该模式在 [LangGraph #6446](https://github.com/langchain-ai/langgraph/issues/6446) 的本地复现中得到验证。
- **读取的隐藏副作用**：API 名称为 get/list 不证明它不改变状态。遇到探测后资源增长或会话变化，比较调用前后的存储；例如嵌套 defaultdict 的索引可能在未命中时创建记录。修复未命中路径后也要确认已有记录、过滤和异步路径正常。参考 [LangGraph #8754](https://github.com/langchain-ai/langgraph/issues/8754)；该公开报告的版本与本地复现版本不同，不外推为所有版本都受影响。
- **恢复位置与重放范围**：确认暂停恢复是从某一行继续，还是从整个节点开头重跑；记录操作身份和已提交效果。若重放范围包含副作用，按业务语义将其移到合适边界，或在真正执行副作用的一侧提供持久、原子的幂等保证。内存 set/list 只能用于局部实验，不能证明进程崩溃或跨实例下 exactly-once。参考 [LangGraph 的中断恢复说明](https://docs.langchain.com/oss/python/langgraph/interrupts)。

这些是有条件的诊断线索，不是遇到对应框架就必须报告的缺陷；正常的快照传递、缓存和幂等重放均可符合契约。

## 不变量与预算

为每条不变量找出建立、保持、检查三个位置。例如：摘要建立 claim-to-source 映射，交接保留映射，回答验证引用对应；标注“摘要有来源”本身不能证明摘要被来源支持。

成本、延迟和重试次数通常是预算，不要求每个节点都保持不变。串行、并行与循环的累计方式不同；记录真实计费次数和关键路径，不把局部平均延迟直接当端到端高分位延迟。

若业务性质尚未明确，先提出可供确认的候选性质，标注为建议，不把自己的偏好判为系统缺陷。

# 输出与验证范式

按任务规模使用。让读者看到可复查的判断依据，不让表格取代因果解释。

## 单个故障的输出

```text
结论：最可能/已证实的失效边界及业务影响。
证据：代码位置、接口定义或运行记录；说明已观察与尚未观察的部分。
机制：触发条件 → 违背哪条契约 → 下游如何误读或放大。
修复：足以解决当前问题的最小修改及涉及的兼容性。
验证：输入与环境、判定器、预期结果、实际执行状态。
剩余不确定性：仍需什么材料，怎样区分剩余假设。
```

合成示例：`search()` 捕获超时返回 `[]`，下游遇到 `[]` 就生成“没有相关记录”。可以通过代码确认失败和无结果共用状态；是否引发了某次线上错误，还需运行记录或复现。修复应传递 `Failed(timeout)` 并定义下游降级行为，不能只改变返回结构而不修改消费者。验证分别注入超时和成功空结果，确认状态不被混淆，且陈述仍限定在检索范围内。

## 架构审查的输出

先说明审查范围、材料和未覆盖部分，再按影响排序给出发现。需要横向比较时使用：

| 维度或边界 | 状态 | 证据 | 影响与优先级 | 修复及验证 |
| --- | --- | --- | --- | --- |
| 具体检查对象 | 已证实问题 / 怀疑 / 未发现问题 / 证据不足 / 不适用 | 可定位的材料 | 业务后果，置信度另述 | 最小改动和可观察判据 |

“未发现问题”仅适用于写明的检查范围。没有日志是证据不足，只有当缺失的观测能力确实阻止关键目标时，才另行报告可观测性缺陷。优先级依据影响范围、触发条件与可恢复性，避免凭理论术语严重程度排序。

用户要求整体判断时，可以概括为“在已检查链路上满足哪些约束，哪些问题阻碍当前业务目标”。只有存在用户认可的评价维度、权重和代表性样本时，才给量化总分。

## 把发现转成测试

| 发现类型 | 测试输入与操作 | 主要判据 |
| --- | --- | --- |
| 错误与无结果混淆 | 同一查询分别返回成功空结果、超时、部分结果 | 下游保留区别，分别执行约定行为 |
| 适配丢失含义 | 带单位、版本、引用或状态的数据经过适配 | 消费者需要的性质仍可验证；无法转换时显式失败 |
| 重试重复操作 | 用模拟服务制造“操作已成功但响应丢失” | 同一逻辑操作仅产生约定次数的效果 |
| 缓存替代采样 | 记录 stub 底层调用与各样本的来源 | 所声明的新样本请求真的调用生成器；重放不被当新证据 |
| 近似路径偏差 | 对新旧路径输入正常与阈值附近样本 | 检查业务级结果和副作用，容差有来源 |
| 多智能体合并冲突 | 构造共享字段不一致及全局预算超限 | 冲突可见并按规则处理，整体约束被检查 |

这些是测试设计，不是已经接入任何项目的测试代码。落地时用该项目真实的接口与断言，区分确定性契约测试、带不确定性的效果评估和运行时监测。记录测试范围、样本及结果，避免声称有限样本证明所有输入正确。

## 重构验收

为具体变更选择所需的验收：

- 拆分/封装：显式输入、状态更新、错误传播与可观察副作用是否保留？
- 模型/提示词/工具替换：数据契约是否兼容，任务级指标是否在约定容差内？
- 并行化：共享状态、执行顺序和资源预算是否允许并行？
- 添加缓存：键与失效规则是否完整，采样语义是否被改变？
- 添加重试：逻辑操作身份、终止条件与副作用是否保持？

这是常见工程变更的检查提示，不是书中“七种重构模式”的复刻。对不能证明等价的变更，明确它是行为改变，给出新契约和验证方法。
