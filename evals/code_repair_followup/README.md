## c06：异步取消与清理

在首批 c05 修复结束、原 36 次实验仍在执行时，维护者从三组提交都使用的取消隔离策略中提出额外时序检查。2026-09-30 16:00 UTC 后，本地复现发现：c06 的预设“正常”实现并不满足全部文字要求。

时序：一个子任务失败 → 组取消兄弟任务 → 兄弟进入异步清理并等待门闩 → 父调用收到恰好一次外部取消 → 原实现再次取消正在清理的兄弟 → 组提前结束且清理未完成。这不需要多次外部取消或永不响应取消的代码。冻结的五项异步验收未组合检查这个交错。

`check_cleanup.py` 保存额外探针；`async_healthy.py` 来自已完成的 c05/B_tools/1 提交，作为修订的可运行正常参考。两者和本目录都不在原冻结清单中。探针只判定退出前清理完成；父取消与已有失败谁优先在原题面不够精确，故接受原异常对象或 CancelledError，不事后偷偷增加优先级要求。

此发现不修改原输入、原评分或剩余调度。原 c06 的“正常不修改”只能解释为预设标签下的描述，不能解释为正确行为；所有正常误报/不必要改动结论需排除 c06 并说明原因。额外探针在全部异步提交上运行并另表报告，不混入原主指标。它是结果启发的开发检查，不能冒充预注册指标或新保留集。

第一轮 c06 产物完成后，维护者又检查了“子任务已自行取消并开始清理，父调用随后收到一次取消”的交错。c06/A_basic/1 仍会再次取消这个子任务、打断清理；修订参考及当时 B/C 提交完成了清理。`check_cleanup.py` 将两个时序分别记录，并要求二者都通过。这是另一项结果启发的探针，不能用其组间差值直接宣称指导增益。

```sh
.venv/bin/python -m unittest evals.code_repair_followup.test_cleanup -v
```

下一轮如继续使用正常异步任务，应使用修订参考及这个探针，并在模型调用前另行冻结。此处不覆盖旧参考、不重新运行原试验，也不据此选择性追加模型尝试。

## c04：提交失败与连接复用

随后审阅第一轮三份 c04 提交时发现，三组都将预设正常实现判为违规，并各自补测了 RELEASE/提交失败。维护者用两个真实 SQLite 连接复现：读连接持有读事务，写连接插入后在最外层 RELEASE 遭遇 SQLITE_BUSY；原实现将 RELEASE 放在异常处理范围外，留下尚未撤销的批次。

`check_transaction.py` 固定 journal_mode=DELETE、零等待超时及普通 records 表，无特殊触发器，也不需要定制数据库连接。它先检查失败批次是否撤销，再释放读锁并复用写连接，检查下一次成功批次能否对另一个连接可见。只撤销行而保留工具自建事务也不够：后续调用可能把残留事务当成调用者外层事务，成功返回却未提交。

该行为与 [SQLite 事务文档](https://sqlite.org/lang_transaction.html) 中提交遇到 SQLITE_BUSY 后事务仍可保持活动一致。`transaction_healthy.py` 保存 c04/B_tools/1 提交作为修订参考；原七项验收和新增探针均通过。此参考仍不承诺在任意 I/O 故障、触发器主动整事务回滚或连接自身拒绝清理时保护一切状态。

```sh
.venv/bin/python -m unittest evals.code_repair_followup.test_transaction -v
```

因此本轮可用于“已知正常保持”解释的预设控制仅剩 c02。c04/c06 的原标签、原分数和逐次判断保留，但相关误报或“不必要修改”解读必须排除二者。修订参考是确定性验证产物，尚未作为新正常输入重新进行三组模型实验。
