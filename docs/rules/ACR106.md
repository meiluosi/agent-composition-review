# ACR106 · 恢复/重放后重启了已完成的节点

**级别**：medium（轨迹检查）
**命令**：`acr trace <trace>`

## 症状

- 运行在 resume / replay 之后，一个已经 `node_end` 的节点又出现 `node_start`。
- 外部副作用重复：同一封邮件发两次、同一个订单建两次、同一个 API 写两次。
- 最终状态看起来是对的，但副作用计数不对；或者新状态被旧的 replay 覆盖。

## 为什么发生

checkpoint 恢复/重放时，执行器应该只重跑未完成的 task。如果恢复边界选错（例如从整个 superstep 重放，而不是从 pending writes 恢复），已完成节点的 side effect 会再次执行。

这类问题属于运行时恢复语义，静态构图规则看不到；需要 trace 里有 resume/replay 标记和节点完成事件。

## acr 输出示例

```text
$ acr trace run.jsonl
7 event(s) (unified) - 1 finding(s): medium 1
  MEDIUM ACR106  Completed node restarted after a resume/replay marker
    event seq 6
    Node 'gate' had already completed before resume marker e5, but started again after it.
  evidence:
    - e2: node 'gate' completed at seq 2
    - e5: resume marker at seq 5
    - e6: node 'gate' started again at seq 6
  fix: Check the resume/replay checkpoint boundary: do not re-run nodes whose writes were already durable.
  docs: docs/rules/ACR106.md
```

## 没有 resume 标记怎么办

LangGraph 默认 debug 输出只有 `task`/`task_result`/`checkpoint`，没有 `resume` 事件。用 `--resume-at` 指向“恢复前最后一条事件”的 `seq`：

```sh
acr trace run.jsonl --resume-at 4
```

它会在该事件后插入一个合成 `resume` 标记，再运行 ACR106；不会改原文件。

统一 JSON 格式也可以直接在顶层写：

```json
{"resume_seq": 4, "events": [...]}
```

也可以尝试自动推断（opt-in）：

```sh
acr trace run.jsonl --infer-resume
```

当同一个 `checkpoint_id` 在 trace 中再次出现时，插入 resume 标记。它是启发式：嵌套/子图 trace 可能出现重复 checkpoint id，所以默认关闭；推断结果需要结合 checkpoint/step 证据核对，不要把它当自动根因结论。

## 最小修复

- 从 pending writes / 精确 checkpoint 恢复，而不是重放整个 superstep。
- 给节点副作用加幂等键，让重复执行成为 no-op。
- 恢复后先检查已完成节点是否被再次调度；必要时在节点内记录 `run_id + node` 完成标记。

## 误报边界

- 只报 trace 中显式出现 `resume`/`replay` 标记，且同一节点在标记前已有**完成**的 `node_end`、标记后再次 `node_start` 的情况。
- **被 interrupt 的 `node_end` 不算完成**：如果 `task_result` 带 `interrupts`，恢复后重启该节点是预期行为，不报 ACR106。
- 没有 resume/replay 标记的普通重试、循环节点不报。
- 如果 trace 的 `node` 字段缺失、或 resume 标记没有 `id`，无法建立前后关系时不报。
- 这需要采集方在 trace 中写入 resume/replay 事件；LangGraph 默认 debug 输出不产生这个标记，需要手动插入或写适配器。没有标记就看不到，不代表运行时没有问题。
