# LG #3875 · interrupt 节点在 resume 后重启（ACR106 负向控制）

**状态**：grounded（ACR106 负向控制；真实公开 trace，0 findings）
**一句话症状**：两个分支各有一个 `interrupt`，恢复后两个节点都重新开始；看起来像“节点重复执行”，但它们在 resume 前只是被 interrupt，并没有完成——ACR106 不应报告。

## ACR 规则 / 命令

- [ACR106 · 恢复/重放后重启了已完成的节点](../rules/ACR106.md)（grounded）

```sh
acr trace evals/realworld3/cases/lg3-3875/trace.jsonl
```

## 证据（acr 0.5.1 当前输出）

```text
$ acr trace evals/realworld3/cases/lg3-3875/trace.jsonl
8 event(s) (jsonl) - 0 finding(s): high 0, medium 0, low 0

timeline:
  #001  e1  node_start  node=branch_1  step=1
  #002  e2  node_start  node=branch_2  step=1
  #003  e3  node_end    node=branch_1  step=1  result=[]   ← interrupts 非空
  #004  e4  resume      step=1
  #005  e5  node_start  node=branch_1  step=1
  #006  e6  node_start  node=branch_2  step=1
  #007  e7  error       node=branch_1  step=1
  #008  e8  node_end    node=branch_2  step=1

  No runtime composition issues found.
```

关键在 `e3`：`branch_1` 的 `node_end` 带 `interrupts`，它是**被中断**，不是 completed；resume 后重启属于预期行为。v0.3.1 修复的正是把这种 `node_end` 误当完成的误报。

## 最小修复

这个案例**不需要修复图**，也不应为了让 ACR106 沉默而删掉 `interrupts` 字段。需要记住的是：

- resume/replay 后的重启不等于重复副作用；先看节点在标记前是否真的完成。
- 如果业务担心恢复副作用，用幂等键/完成标记，而不是禁止 interrupt 重启。

## 验证边界

- 这是**负向控制**：真实公开 trace 在修复后 0 findings。去掉 `interrupts` 字段会复现 1 条 ACR106 误报（见报告第 5 节），说明该案例确实约束了规则。
- trace 是从 issue 正文归一化的，不是 reporter 提供的 `acr` 输入格式；resume 标记来自 issue 文本中的恢复操作。
- ACR106 还要求 trace 有显式 resume/replay 标记；LangGraph 默认 debug 流不产生该标记，需要适配器或手动插入。
- 不把该 issue 判成 ACR 能“检测”的故障；它在这里的价值是证明规则不过度报告。
